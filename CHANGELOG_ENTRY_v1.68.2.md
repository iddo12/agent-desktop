## v1.68.2 - Handoff: messages typed during a handoff are held, no duplicate handoff request; messages written just before a link dies are re-sent (2026-10-03)
Sandbox run of the combined branch (Security/work/sandbox_integ_cpuguard_reconnect_speed_2026-10-03.md) found three bugs. All fixed here.
- **B1 (high) message typed during a handoff:** `sendOrHold` took the "agent is idle, send now" shortcut BEFORE the handoff-flow check, so for an idle agent the text was typed into the pty being stopped (lost) or answered by the old session. The flow gate now comes first: the message is held visibly, parked (kept on disk, counted in the handoff banner) and delivered to the fresh session after the reset. New pure helper `HandoffLogic.flowHoldsMessages`, export `window.guardsFlowActive` (only saving/resetting/resuming flows and a pending resume; the near-handoff and "Handoff all" cases keep the old behaviour).
- **B2 (medium) duplicate handoff request:** a handoff prompt typed but left unsent in the input box (the stuck-Enter check arms one write at a time) used to give up after 3 attempts and the flow then typed a second prompt. Now (a) while a typed prompt is not yet in the transcript the delivery looks at the input box and presses Enter itself (`nudgeSubmit`, at most every 6 s, only when the screen shows exactly that prompt), and (b) the "write it now" nudge is allowed only after the first request is confirmed in the transcript (`HandoffLogic.mayNudge`). The first request keeps one hid for the whole flow and is typed once.
- **B3 (low-medium) message lost in the detection window:** when the attach process died, a message written in the seconds before the app noticed was left as "Not confirmed - Resend now". `onAttachFailed` now hands such a write back to the queue (`requeueSince`, same path as the dead-link restart) unless the transcript already has it, and cancels its dead-link/stuck timers; it is sent once the link is back.
- **Fork cost (42K tokens) investigated, left as is:** the app never passes `--fork-session`; recovery runs `claude --bg --continue` (or `--resume <id>`), and the CLI itself starts a new session file that continues the conversation. The cost is the new process re-reading the context (cache re-creation), which any restart pays. Not avoidable from the app without changing the CLI's behaviour.
- Tests: handoffLogic (flow states, mayNudge, sendOrHold order check), handoffDelivery (Enter on an unsent prompt, typed once), connectionHealth 19-20 (requeue on attach failure, not when already in the transcript). All fail before the change.
- **Re-run in the sandbox with a working agent:** idle-agent and working-agent message during a handoff; handoff prompt colliding with a message; dead pty with a message typed in the 12 s window.
